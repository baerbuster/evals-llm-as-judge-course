# Evals and LLM-as-Judge

A two-lesson course for someone who shipped an AI feature and cannot tell if it is getting worse.

**Capstone:** a working grader that prints real precision and recall.

The tool being graded is a fake poem writer. A person describes a moment from their life, it returns
a four-line poem. Five saved runs of its output ship as fixtures, oldest to newest, and it gets worse
across them. Run 5 is the one the learner is asked to diagnose, and every output in it carries a
human pass/fail label on all seven criteria.

The lessons, the diagrams, and both build-alongs were generated by the pipeline in `agent/`.

## Run it

Python 3.12. Run both commands from this folder, the one holding this README.

**Nothing to install and no API key.** Both build-alongs default to replay mode and read the judge's
cached replies from `build/judge/responses/`. They import nothing outside the standard library, so
they run on a clean 3.12 with no packages installed. `requirements.txt` is for the generator in
`agent/`, not for these.

Build-along 1, the deterministic grader:

```
python -m build.grader.grader build/fixtures/runs/run5.json
```

Build-along 2, the same grader with an LLM judge added, which completes the capstone:

```
python -m build.judge.judge build/fixtures/runs/run5.json
```

### What you should see

`output/buildalong1.txt` and `output/buildalong2.txt` are what those two commands printed here. The
first run of each from this zip reproduces its file exactly.

You have reached the capstone when the second command ends with the judge measured against the human
labels and the history read back:

```
judge trust  tp 16  fp 1  fn 1
precision: 0.94
recall: 0.94
run   shape  line_length  no_preamble  no_copy  specific  mood  no_advice  pass_rate
run1  0      0            0            0        0         0     0          1.00
...
run5  4      3            5            1        10        3     4          0.25

== judge step 8: the answer you came for ==
runs in history: 5
trending down the most: specific +10  pass rate 1.00 -> 0.25  getting worse: yes
```

Two notes on repeat runs. Each build-along appends one row to its own `history.csv`, which ships
holding the four earlier runs and gains run 5 when you run it. Running the same saved run again will
not add a second row for it, so the output stays identical. Point either command at `run1.json`
through `run4.json` and it grades that run instead and adds its row.

Live mode exists but is not needed to review. `--live` on the second command calls the API, needs
`ANTHROPIC_API_KEY` and `pip install -r requirements.txt`, and overwrites the cached replies.

## Checkpoints

A checkpoint is something the learner can do afterward and could not before. Six of them, three per
lesson, each with a visible check the build-along prints. Full versions with their before, after, and
test are in `agent/checkpoints.md`.

**Lesson 1, the deterministic grader**

1. Write a pass/fail rule for a single output that a second person could apply and reach the same
   verdict.
2. Run those rules over a set of outputs and list every case where a rule's verdict disagrees with
   their own label.
3. Sort every failure into a named bucket, append the run to a history of every past run, and read a
   run-by-category table to say whether the tool is getting worse and in which bucket.

**Lesson 2, the judge**

4. Write a judge prompt that returns a pass/fail verdict for a criterion no code rule can check.
5. Compute the judge's precision and recall against a set of human labels.
6. Separate the judge's false positives from its false negatives, name a different fix for each, and
   append the judge's verdicts to a run-by-criterion history table that says whether the tool is
   getting worse.

Each checkpoint came from a named breaking point, a place a learner gets stuck or nods along without
understanding. Those are in `agent/breaking_points.md` and were written before any content.

## The capstone, and why it is cut in two

The capstone is one grader, run from the command line, that loads a saved run, applies code rules and
an LLM judge to every output, sorts failures into categories, measures the judge against human labels,
lists its two kinds of mistake separately, appends one row per run to a history table, and says which
criterion is trending down the most. `agent/capstone_spec.md` fixes what it takes in and prints.

It splits into two pieces, one per lesson, and each is useful on its own.

**Piece 1, the deterministic grader.** Code rules over every output, disagreements against the human
labels, failure categories, and a history table with a trend line. It stands alone because a learner
holding only this can already answer "is it getting worse, and in which category" for every criterion
a rule can check, which is the question they walked in with.

**Piece 2, the LLM judge.** A judge for the criteria no rule can check, its precision and recall
against the human labels, its false positives and false negatives as two separate lists, and a second
history table with the judge's columns beside the code rules'. It is built second because a judge is
only worth adding once there is a history table shape to put its columns into and human labels to
measure it against, both of which piece 1 produced.

**They compound rather than restart.** `build/judge/judge.py` opens by importing the grader the
learner wrote in lesson 1:

```python
from build.grader.grader import (
    OUTPUTS, RUN, RULES, VERDICTS, CATEGORIES, CATEGORY_OF_RULE,
    LABELED_RUN, LABELS_PATH, HISTORY_PATH, HEADER,
    print_verdict, print_table, read_history,
)
```

It never copies that code and never edits it. The first thing lesson 2 prints is lesson 1's whole
output, which is why `output/buildalong2.txt` opens with the seven steps from `output/buildalong1.txt`
before its own eight begin. The two pieces keep separate history files; neither writes the other's.

## How it was generated

Everything in `course/` and `build/` came out of the pipeline in `agent/`. One command runs all of it:

```
python -m agent.run all
```

That needs `ANTHROPIC_API_KEY` and the two packages in `requirements.txt`. It is not needed to review
the course, and running it would regenerate the course from scratch.

The pipeline is one plain loop with the retries visible, in `agent/run.py`. Each stage builds a prompt
from the design files plus only the context that stage is allowed to see, calls the model, saves the
raw reply, splits it into files, and runs checks on the result. Every check failure goes back to the
model as a specific sentence and it rewrites, up to three attempts.

Three things in it are worth a look:

- **The checks are the quality bar**, in `agent/checks.py`. Word counts, format markers, and the
  banned quiz blocks are deterministic. The build-along check goes further: it runs the generated code
  after every step in a scratch copy and compares what it actually printed against the text block the
  model claimed it would print, so a build-along cannot ship unless it works.
- **The pipeline uses a judge on itself.** Three checks are model calls, because no code can read prose
  and settle them: whether lesson 2 leans on a concept lesson 1 never taught, whether every technical
  term is the industry's rather than one the model coined, and whether the fixtures are hard enough
  that the course's own judge makes a few mistakes on them. The course teaches LLM-as-judge and the
  thing that wrote it uses one.
- **Record and replay**, in `agent/record_replay.md`. The judge's every raw reply was saved during one
  live run. Replay reads those files and hands them to the same parser live uses, so the verdicts,
  both disagreement lists, precision, and recall come out identical and the review costs nothing.

Every raw reply is kept in `scratch/`, beside the files it was split into, so you can see what the
model returned before the pipeline touched it. The build-along replies are the interesting ones. The
model could not know what the judge would say, so it wrote those output blocks as marked guesses, and
after the live run the pipeline replaced them with what the code really printed. This shows both:

```
diff scratch/lesson2/raw/buildalong.txt scratch/lesson2/buildalong.md
```

`agent/pipeline.md` has the full stage table and the reasoning.
